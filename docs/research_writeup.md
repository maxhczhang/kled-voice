# Audio Integrity Lab Research Writeup

This document is a living design note for the Audio Integrity Lab audio fraud detection prototype. It explains the problem, threat model, technical choices, evaluation plan, and limitations behind the system.

## Problem Statement

Platforms that accept user-generated voice need a way to identify suspicious audio submissions, especially as text-to-speech and voice cloning tools become easier to use. For a product expanding from image workflows into voice workflows, audio trust becomes similar to image authenticity: the platform needs early warning signals before synthetic or manipulated content affects users or downstream systems.

Audio Integrity Lab explores a practical baseline for detecting synthetic, cloned, replayed, or suspicious speech. The goal is not perfect attribution or identity verification. The goal is to produce a measurable risk signal that can support review, moderation, or trust-and-safety workflows.

## Threat Model

The first version focuses on flagging audio that may be:

- generated by text-to-speech systems
- produced by voice cloning tools
- replayed from another recording
- heavily compressed, edited, or spliced
- low quality enough to make authenticity uncertain

The first version does not attempt to solve:

- legal identity verification
- guaranteed speaker verification
- attribution to a specific generation model
- fully adversarial deepfake detection
- real-time streaming fraud detection

## Initial Technical Approach

The project starts with an auditable baseline before moving into heavier models. This makes the system easier to evaluate, debug, and explain.

Planned pipeline:

```text
audio input
  -> load and resample
  -> trim / normalize
  -> extract acoustic features
  -> optionally extract Wav2Vec2 embeddings
  -> classify real vs suspicious/synthetic
  -> output risk score and explanation signals
```

The repository now includes the first implementation of this baseline pipeline: audio loading, acoustic feature extraction, manifest loading, and sklearn training/evaluation scripts. The current starter manifest contains only a generated test tone, so it verifies the pipeline shape but does not yet support real model training.

## Feature Rationale

MFCCs are a standard compact representation of speech timbre and spectral envelope. They are useful as a baseline because many synthetic artifacts appear in frequency-domain speech structure.

Mel spectrogram statistics provide a broader view of energy across perceptual frequency bands. They also support visual inspection in the demo.

Spectral centroid, rolloff, zero-crossing rate, and RMS energy give lightweight indicators of frequency balance, high-frequency behavior, noisiness, and loudness consistency.

Wav2Vec2 embeddings provide pretrained speech representations learned from large-scale audio data. They may capture speech patterns that handcrafted features miss, but they should be evaluated against simpler baselines rather than assumed to work automatically.

## Model Strategy

The first model should be simple:

- logistic regression for a transparent baseline
- random forest for nonlinear feature interactions
- later, a small neural classifier on Wav2Vec2 embeddings

Starting simple helps separate data quality, feature quality, and model complexity. If a simple baseline performs poorly, a deeper model may only hide the problem instead of solving it.

## Evaluation Plan

The detector should be evaluated with a held-out test split and metrics that match fraud detection workflows.

Primary metrics:

- ROC-AUC
- precision
- recall
- F1 score
- confusion matrix

Operational metrics:

- feature extraction time
- inference latency per clip
- supported audio formats

ROC-AUC is especially important because fraud systems often operate with adjustable thresholds. The model needs to rank risk well, not just produce one fixed binary decision.

## Product Decisions

The system should return a risk score rather than only a binary label. This better matches moderation and trust workflows, where uncertain cases may need review instead of automatic rejection.

The demo should show explanation signals and spectrograms so a reviewer can understand why a clip was considered suspicious. These explanations are not proof of fraud, but they make the model output easier to inspect.

## Limitations

Audio fraud detection is adversarial and changes quickly. Synthetic speech generators improve over time, and a model trained on one dataset may not generalize to another.

Potential limitations include:

- dataset bias inflating evaluation results
- degraded performance on noisy or compressed uploads
- false positives on unusual real speakers or recording setups
- false negatives on high-quality synthetic voice
- poor generalization to new synthesis models

Because of these limitations, Audio Integrity Lab should be treated as a prototype risk-scoring system, not a final authority on whether a voice recording is fraudulent.

## Future Work

Planned extensions:

- evaluate on ASVspoof or another public anti-spoofing benchmark
- add model calibration for better risk scores
- compare handcrafted acoustic features against Wav2Vec2 embeddings
- support batch scoring
- add a Streamlit or FastAPI demo
- analyze false positives and false negatives
- explore speaker consistency checks across multiple clips
